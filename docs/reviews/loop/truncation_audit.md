# P1-08 — Truncation & padding-in-loss audit (length measurements)

Generated by `scripts/measure_truncation.py` (measurement only — no training, no evaluation, no model reruns). Machine-readable twin: `artifacts/manifests/truncation_audit.json`.

## What the trainer actually does (read from source)

- Encodes `prompt + '\n' + reference_code`, then a hard slice `ids[:128]` (`trainer_slices_at_max_len=True`).
- **No explicit EOS token** is appended: the only prompt/code separator is the single newline from prompt_marker, and truncation is a hard slice ids[:max_len].
- Batches are zero-padded to the batch max (pad id 0 = '\x00', i.e. NUL).
- Loss has **no ignore index** (`loss_ignore_index_present=False`): GPT.forward computes F.cross_entropy(logits[:, :-1], targets[:, 1:]) over every position — padding targets (id 0 = NUL) contribute to the loss.
- Examples shorter than 4 tokens are dropped (`examples_shorter_than_4_dropped=True`).

## The one truncated operation, in detail

- `sum_of_abs`: 40 truncated records, 1 distinct program(s) among them.
- prompt 58 tokens + program 114 tokens = 172 combined; the 128-window keeps 70 program tokens and cuts **44**.
- kept tail ends: `'    total = 0\n    for x in a:\n        if x < 0:\n            total = total + (-x)'`
- cut tail: `'\n        else:\n            total = total + x\n    return total'`
- i.e. training never shows a *completed* program for this operation: the sequence stops before the `else` branch and the `return`.

## Reading (honest scope)

- These are measurements of the regenerated train sets built by the scripts' own split code from recorded configs/seeds; like the novelty audit, the historically scored splits were never archived as files, so this audits the deterministic regeneration, not an archived original. The rebuilt tokenizers match the on-disk `pilot_tok.json` and `surface_tok.json` vocab-for-vocab, which corroborates the regeneration (for the surface arm the n60 and n130 vocabularies are identical, so that match corroborates the corpus, not the `n_per` choice — `n_per=60` comes from the recorded manifest).
- **Pilot and Stage-3 surface: no truncation.** Every one of the 1,400 pilot and 600 recorded surface training records fits inside 128 tokens (longest combined = 109, `cond_abs_max`), so every program the pilot/surface models were asked to learn has complete coverage in the training window. For those arms the 128-token window is not a confound.
- **The composition-0.000 baseline is also untruncated.** `scripts/run_composition.py` trains on the same primitive split as `pilot_train.jsonl` (provenance check above), which has 0 records over 128 — so training-time truncation cannot explain the held-out composite 0.000, and we do not claim it does. (The decode ablation narrowed *inference-time* stopping; it did not test training-time truncation. The two are separate questions.)
- **One operation IS truncated: `sum_of_abs` in the Stage-4 exposure arm.** All 40 of its training records exceed the window and lose the last 44 program tokens — the `else` branch and the `return` — so training never shows a completed program for that operation. This is a real coverage defect *for that arm and that operation*. It is also the one exposed operation the decode ablation reports failing on its own training instances; that correlation is suggestive, but we ran no ablation (retrain with a longer window) and therefore do not claim truncation *caused* any score.
- Truncation counts say how many training records lose program tail tokens at the 128-token window; they do **not** by themselves show that any measured score was caused by truncation — that would need an ablation (longer window / no truncation), which we did not run.
- The padding share is a share of *loss target positions*, computed under the trainer's exact batching rule; it is not a share of the loss *value* (we did not run the model to decompose the loss). Padding targets are token id 0 (NUL), so every padded row trains the model to predict NUL after a sequence's last token. We report this as a property of the objective, not as an explanation for any particular evaluation result.
- The decode ablation narrowed *inference-time* stopping; it did not test *training-time* truncation. The two are separate questions.
